# 从本次 π₀ 微调到下一次 π₀.₅ 微调：经验总结

日期：2026-11-02。本文件是基于现有代码和实验记录整理的中文研究备忘，不表示 π₀.₅ 已完成适配，也不启动下一轮训练。[维护版英文总结](../../docs/pi0-to-pi05-finetuning-lessons.md)提供同一主题的源码和证据导航。

## 一、这次工作最有价值的经验

微调工作需要同时打通数据、训练、执行和评估。模型能降低 loss、专家轨迹更平滑、视频看起来更顺，都只是其中一层证据。下一次应该先建立一个可解释的最小闭环，再逐步加入优化，避免同时改变数据、损失、动作块和控制参数，最后无法判断是哪一项起了作用。

本次形成了 Mac 仿真与云端 GPU 训练／推理链路，最新训练集包含20条完整演示和2条纠正轨迹，共23,859帧。最终24次验收中，candidate999＋2倍手腕阻尼取得12/12成功，v6为10/12，典型物理 jerk 降低16.4%，最坏尖峰降低22.5%。但典型降幅没有达到冻结的20%门槛；后来按用户明确选择采用该组合作为运行流程。**使用选择与实验验收通过需要分别记录。**

## 二、下次应该直接复用的工作方法

### 1. 先检查数据契约，再考虑训练参数

必须写清楚每一帧的含义：图像和状态是在动作前还是动作后采样，标签是请求动作还是限幅后实际下发的动作；关节顺序、单位、夹爪开度、绝对／增量控制、采样间隔分别是什么。

本次采用动作前的图像／状态，与同索引实际执行的绝对关节目标对齐。下次不一定必须采用相同接口，但必须让采集、导出、训练 reader、归一化和推理反变换保持一致。不能仅凭“成功转换成 LeRobot”就认为接口正确。

建议先抽查整条演示与阶段边界，执行图像像素、state/action、时间戳和归一化往返检查；动作块末尾不得串入下一条 episode，重复填充的标签需要与损失掩码方案相容。

### 2. 增加独立覆盖，比单纯堆帧更重要

23,859帧不等于23,859个独立场景，22条训练片段也不等于22个全新布局。来自同一父布局的纠正片段仍高度相关。训练／验证／测试应先按父轨迹或布局划分，再在训练侧补采。

本次50个指定 OOD 场景成功31次：位置10/20、朝向12/20、外观9/10。19次失败中18次没有抬起目标。它提示下一轮优先补足位置、朝向、接近和闭合阶段的覆盖；没有同批v6对照，因此不能说候选的泛化已经提升。

下次应在采集前做覆盖表，把位置、朝向、物体、视觉条件、失败恢复和释放撤离分别列出。先补哪一类，由失败阶段决定，不规定一个未经验证的“最低演示条数”。

### 3. 专家变平滑，不代表策略闭环也会变平滑

本次连续运输路径和 IK 重标注改善了教师轨迹，20条完整标签通过审核；但随后学习策略的运动指标并没有自动得到对应改善。教师指标、离线拟合和策略闭环是三项不同检查。

下次可以继续优化演示，但每次重标注后都要保留原数据版本，并安排同初始化、同预算、同归一化规则的对照。不能用专家 jerk 的降幅代替模型执行的降幅。

### 4. 归一化文件应当与权重一起管理

本次旧统计中近乎恒定的动作维度曾出现约2.735×10⁻⁵的标准差，使新纠正动作映射到约280量级的归一化目标。之后使用了独立版本的标准差下限并重新训练、评估。

这个经历说明需要检查**经过实际动作变换后的分布**，不说明0.01是所有任务通用的下限。π₀.₅要重新核对它的数据变换和新数据分布；继续训练是否沿用旧统计，应依据兼容性检查决定。

还要区分“JSON数值相同”和“文件字节相同”。本次源统计与checkpoint统计有已确认的序列化差异；按字节哈希核验服务时，仍必须使用对应checkpoint保存的资产。

### 5. 显存可行性要做真实 probe，不能照抄8×2

本次长动作块训练实际选择了microbatch8×梯度累积2，有效batch16；模板里暂定的2×8不是最终实测选择。下一次应重新测试π₀.₅的token长度、动作块长度、精度、可训练模块和后端。

probe至少区分首次编译和稳定更新，记录真实张量形状、有限loss／梯度、显存峰值、优化器更新耗时、checkpoint写入和磁盘余量。梯度累积步数不等于优化器更新次数；冷启动耗时也不能直接作为长期吞吐。

### 6. 训练参数选择要看真正的可训练参数树

本次是语言模块与动作专家的LoRA，加状态／动作相关映射层训练，不是所有层全量更新。下一次不能只复制正则表达式或看到配置写了“LoRA”就认为训练范围正确。

需要列出实际参与更新的模块、参数数量，并在短probe中检查目标模块有有限且非零的梯度、冻结部分没有意外变化。先建立简单的官方兼容微调基线，再决定是否加入加权损失、时间差分约束或阶段重采样。

### 7. 分开诊断模型预测、执行调度和物理接触

ACT辅助实验训练了20,000步，训练布局0/4、验证尝试0/12完整成功。进一步检查发现：24个策略状态中，前25步都没有充分开夹，22个却在后75步预测了开夹。每25步重新规划，会让后段释放计划反复延后。

完整100步的局部回放在6个状态都曾释放，但两秒窗口内完整成功仍是0/6。另有夹爪与盒底接触，开夹目标较大，实际开度却受到限制。**这些是有用的定位证据，并不是ACT证明数据质量通过。**

下次遇到类似问题，应对齐预测块、实际执行前缀、关节状态和接触力；随后通过固定权重的完整闭环执行对照验证。不能只加开夹命令，也不能直接认定需要更多训练。

### 8. 物理抖动、任务停滞和真实卡顿要分别衡量

仿真时间里的jerk反映物理运动变化；低运动阈值反映特定定义下的停顿；实际动作应用间隔和推理等待反映墙钟时间。它们不能互相替代。视频按仿真时间编码，不能完整展示网络等待。

本次最终验收里，候选无运行中推理断档，v6出现过一次约0.683秒等待；但单个事件不能证明网络时延问题已经被模型解决。下次应同时保存动作／状态、阶段、接触、推理往返与实际控制间隔，并把预热和正式计分分开。

### 9. 模型改进与阻尼改进需要分开归因

candidate999和2倍阻尼是“权重＋仿真动力学”的组合。组合效果可以用于选运行方案，但不能把全部收益写成模型训练收益，也不能假定相同阻尼适用于另一台机器人。

下次比较π₀与π₀.₅的模型效果时，先固定控制器和执行方式。若同时研究阻尼，就另设对照或使用模型×阻尼的组合实验。当前π₀最终流程可作为系统参考，但不能用不同控制器的结果来宣称模型单独更强。

## 三、π₀.₅迁移时必须重新确认的内容

对照本地固定版本及2026-11-02查阅的[官方模型配置](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/models/pi0_config.py)和[训练配置](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/training/config.py)，本次适配层不能直接改名复用：

| 检查项 | 本次π₀情况 | 下次π₀.₅要求 |
| --- | --- | --- |
| 初始权重 | v6及其候选延续权重 | 选择真正兼容的π₀.₅ checkpoint/config，不把candidate999改名当π₀.₅ |
| 状态输入 | 连续状态投影进入动作侧 | π₀.₅默认启用离散状态输入，但具体任务配置可能覆盖；例如所查LIBERO配置显式关闭，须跟随选定配置 |
| 时间条件 | π₀的状态／动作时间投影分支 | π₀.₅采用adaRMSNorm时间条件；检查实际`time_mlp_*`等参数，不能照搬旧冻结规则 |
| token预算 | 所查π₀默认48 | 所查π₀.₅默认200；实际长度和显存仍要测，不能认为每个任务必须相同 |
| 训练与服务适配 | `banana_config.py`强制`pi05=False`；服务／客户端声明原版π₀ | 为π₀.₅设计独立、真实的模型配置和元数据验证；不要伪装成π₀来绕过检查 |
| RTC | 当前`rtc_policy.py`明确拒绝π₀.₅和PyTorch模型 | 先用兼容的基础推理链路；需要RTC时单独移植与验证，不直接删除保护条件 |
| ROI、100步动作块、8×2、3Hz滤波、2倍阻尼 | 本次任务下选用的工程参数 | 作为候选经验，不当成π₀.₅默认或最优值 |

本次上游固定commit为`215abfb217dbac7d5f1273282331b9b1866c0479`。下一次先决定使用哪个上游版本及JAX／PyTorch路径，并固定版本；不要一边升级依赖、一边移植适配、一边训练。官方提供[π₀.₅基础微调流程](https://github.com/Physical-Intelligence/openpi#fine-tuning-base-models-on-your-own-data)，应以所选版本的具体配置为起点。

## 四、建议的下一次实施顺序

1. **固定任务与评价方式**：机器人／控制器、相机、动作语义、成功判定、超时及数据划分先明确。
2. **跑通π₀.₅最小推理**：确认真实观测能生成维度和数值正确的动作，训练与推理变换一致。
3. **完成数据审计**：抽查整条episode和阶段边界，验证对齐、归一化、padding、父布局划分。
4. **完成真实小probe**：确认预期参数被训练，显存、稳定速度、保存与磁盘余量可行。
5. **训练一个简单基线**：先用选定的官方兼容目标，不同时加入多项自定义改动；训练预算根据probe和早期验证决定。
6. **先诊断训练布局闭环，再做验证**：少量训练布局成功只能说明局部能力，不能当泛化结果。最终测试集保持未用于调参。
7. **依据失败阶段单独改动**：抓不起查覆盖／接近／闭合；预测会放却不放查执行与接触；控制间隔长查推理与本地调度。
8. **按冻结标准做匹配对照并交付**：保留失败和录像，记录数值通过与使用选择的区别，提供独立回退入口。

这些是建议步骤，不是已完成的π₀.₅工作。当前六个验证布局已经反复用于π₀实验，不能重新命名为π₀.₅的全新独立测试集。

## 五、开训前和交付前的检查清单

- [ ] 上游commit、后端、真实π₀.₅权重与配置相互匹配。
- [ ] 图像／状态／动作对齐，单位、顺序、绝对／增量与夹爪语义明确。
- [ ] 训练／验证／测试按父布局隔离，统计只用训练侧。
- [ ] 归一化经过实际变换审计，checkpoint与资产版本绑定。
- [ ] 可训练参数及梯度检查通过，不把旧π₀投影规则直接复制过去。
- [ ] 真实probe记录显存、稳定更新速度、动作／token形状和磁盘余量。
- [ ] 初始化、预算、采样及控制器对照明确，一次只改一个待研究因素。
- [ ] 完整闭环成功与释放／稳定条件有效，不拿loss或局部释放代替任务成功。
- [ ] 物理运动、阶段进度、真实控制间隔与推理等待分别记录。
- [ ] 保留选中及回退checkpoint、匹配资产、完整验收和诊断失败；清理前做依赖检查。

如果出现模型／资产不匹配、非有限数据、episode串接、数据泄漏、可训练范围不符或显存／存储不足，应先停在预检阶段修复，而不是继续长训练。本次数据上传后出现Parquet损坏的经历也说明：读取失败要先查文件完整性，不能误判成模型不收敛。
